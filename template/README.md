# Test kit

This kit supports scoped testing and a clear return of the tester's experience. Its confirmed purpose and permissions belong in [SCOPE.md](SCOPE.md); procedures and expected results belong in [RUN.md](RUN.md).

## Kit identity

- Kit version [required]: Unknown — owner confirmation needed.
- Kit language [required]: English in this source template; confirm for the generated kit.
- Readiness [required]: Draft — scope, version, and procedures are not yet confirmed.
- Readiness limits [required]: Unknown — identify affected scenarios in [RUN.md](RUN.md#scenarios).

Generated explanations, forms, and the fictional example follow an explicitly requested output language, otherwise the user's established working language, otherwise English. Preserve filenames, commands, code, identifiers, and original logs or quoted evidence exactly. Label translations and retain their source evidence; never translate command syntax.

## Where to write

- [Actual feedback record: FEEDBACK_####.md](FEEDBACK_%23%23%23%23.md) starts blank and Not run. Use the owner-confirmed version filename in a generated kit.
- [Fictional writing example: FEEDBACK_TEMPLATE.md](FEEDBACK_TEMPLATE.md) is optional reference material, never a real result or submission destination.
- [HANDOFF.md](HANDOFF.md) links real feedback to the next decision and responsible role.

Both feedback files remain in the kit at separate real paths. Never overwrite the example with real data or use its claims to fill missing records. `####` is a replacement marker, not a four-digit requirement. Before use, confirm a safe, non-sensitive version filename that conflicts with neither the example nor existing names or real paths, including names treated as equivalent by the filesystem. If unknown or conflicting, hold filename finalization and delivery readiness for owner clarification; do not invent a version or suffix, overwrite, or repurpose an existing file. Already confirmed, collision-free values need no repeat approval. Update this document, HANDOFF, and every other reference to the real version filename, URL-encoding special characters in link paths.

The public template contains no test program. A generated kit's `repo/` contains only the authorized copy. Keep kit documents and feedback outside `repo/`. Creating a kit grants neither permission to run it nor permission to send or publish it.

## Start testing

1. Check this kit's identity, confirmed version, actual feedback destination, language, and [scope](SCOPE.md#purpose-and-boundaries). Hold affected testing if its version or record destination is unresolved.
2. Read [RUN prerequisites and dependency versions](RUN.md#environment-and-dependencies), then check current state through the permitted methods there. Required versions and observed installed versions are different facts. If the check is unknown, record the missing information rather than inventing a command.
3. Follow evidenced setup and installation methods within existing user authorization and environment policy. Do not demand repeat approval for an already authorized routine step. Hold only actions whose target, impact, cost, or permission is unclear; do not improvise upgrades or global environment changes. Dependency-free document or manual tests need no package installation.
4. If preparation fails, record the actual attempt, known error, blocked stage, and feature tests Not run in the actual feedback file. Setup success does not establish feature success. Independent, ready scenarios may continue within scope; diagnosis and retries are optional.
5. Perform ready scenarios and record actual actions, feelings, observations, and evidence. Stop affected actions when prerequisites or permissions no longer hold. Observations outside a listed scenario are welcome if found while reading or acting within scope; they do not authorize extra testing.

The tester can provide a round header and one feedback item, including a short conversational reply. A recorder preserves the reply and marks gaps Unknown; acceptance and handoff do not wait for every field to be supplied. Do not invent the tester's experience or expectation.

## When the user declares testing finished

An explicit request such as “finish testing” starts this closeout. Closing an app or conversation does not guarantee cleanup, and unobserved closure is not evidence of a finished session.

1. Stop initiating tests, retries, and new paid work. Inspect the current state of existing work where possible. The finish request alone does not authorize cancellation of unknown external jobs.
2. Tidy only work confirmed to have been started by this test session, using the known [RUN methods](RUN.md#methods) and applicable permissions. Do not blanket-stop shared services, remove dependencies, roll back global settings, or delete logs. If ownership, a stop method, or permission is unclear, record the remaining state, limitation, and needed action.
3. Preserve the original feedback in its current round. Keep observations, feelings, tester expectations, requests, and hypotheses distinct. Append the declared finish and time, actual cleanup state, Not run and unresolved items, and remaining jobs or steps. Do not require diagnosis, repeated reproduction, every scenario, or attachments to finish.
4. Map necessary, permitted evidence already available using [item/source/copy correspondence](FEEDBACK_%23%23%23%23.md#evidence-mapping). Before returning attachments, record [review of the actual return copies](HANDOFF.md#attachment-return-review); withhold unsafe or unreviewed copies and finish the report. State attachment absence and any limitation. Do not restart tests or paid calls to obtain attachments, and never cite fictional example evidence as real.
5. Save the real feedback and a concise [handoff](HANDOFF.md): original item link, needed decision or next action, role, and actual status. If no action is needed, state that with its basis. A full retelling is optional.
6. Report the actual saved locations, minimal return list, Not run or unresolved summary, and remaining work state to the user. The default return list is the actual version feedback, HANDOFF, and any necessary permitted attachments. Add other files only for a stated need within permission; do not automatically include the whole `repo/` or the fictional example. If saving failed, report what was captured and where and why saving was blocked instead of claiming it was saved.

Finish does not mean pass, all jobs stopped, saved, sent, or reviewed. External sending is a separate action governed by existing transmission authorization and available tools. Mention remaining jobs even when document closeout is complete.

A repeated finish request reports existing records and any currently observable remaining state; it must not replay tests or duplicate feedback. Restart only on the user's new instruction. Under the same test basis, append a new round to the same version file and preserve earlier finish records.

## Maintaining this kit

Readiness is Draft, Partly ready, or Ready, with evidence and limits; it is not an execution result. A change to the copied target, scope, procedures, or expected results needs a new output and owner-confirmed kit version, preserving the previous kit and records. Additional rounds, attributed analysis, or handoff updates under the same basis keep the same version. A proposed acceptance criterion does not retroactively change earlier judgments.
